# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

SalahBuddy is an iOS (SwiftUI, iOS 18+ since v5 — SPEC-V5 §9-04) prayer-tracking app: you log each of the five daily prayers by snapping a photo, earn XP scaled by how early in the window you pray, and keep all five together with a small "circle" of friends. Bundle id `org.amacvoters.salahbuddymock`; TestFlight today.

Since v4 this is a **monorepo**: the iOS app at the root, a **Supabase backend under `backend/`** (Postgres + Auth + Storage + Realtime + Deno edge functions), and a circle that can be either **simulated locally** (demo, `BuddySimulator`, exactly as v3.9 shipped) or **real friends on real devices** (`Sources/Core/Sync/`). A solo user still needs no account and the app still works fully offline — the backend only enters the picture at the social boundary. `SPEC-V4.md` is the contract; `backend/README.md` is the backend's own manual and is more detailed than this file.

## Build, run, test

The Xcode project is **generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen) from `project.yml`** and is **git-ignored** (`*.xcodeproj` is in `.gitignore`). Never hand-edit the `.xcodeproj`; edit `project.yml` and regenerate.

Prefer the **`Makefile`** wrappers — they regenerate the project and resolve a concrete simulator automatically:

```bash
make generate   # xcodegen generate (run after editing project.yml / adding files)
make test       # regenerate + build + run the unit tests on a simulator
make build      # regenerate + compile-only check on a simulator
make hooks      # one-time per clone: activate the pre-push hook (see CI below)

# Override the simulator (default "iPhone 16 Pro"):
make test SIM="iPhone 17"
```

Raw xcodebuild, when you need it:

```bash
# Build + run on the connected iPhone 16 Pro (preferred for device runs per global prefs)
xcodebuild -project SalahBuddy.xcodeproj -scheme SalahBuddy \
  -destination "platform=iOS,id=00008140-00164CAC26E3001C" build
# then: ios-deploy --bundle <built .app>

# Run a single test class / method
make test  # ...or, against a resolved sim UDID:
xcodebuild test -project SalahBuddy.xcodeproj -scheme SalahBuddy \
  -destination "platform=iOS Simulator,id=<UDID>" \
  -only-testing:SalahBuddyTests/GameEngineTests/testTierBoundaries
```

**Simulator destination gotcha:** `-destination "platform=iOS Simulator,name=iPhone 16 Pro"` **fails (Error 70 / "ambiguous")** when that device is installed under multiple OS runtimes. Pin a UDID (`id=...`) instead — the `Makefile` resolves one at runtime (preferring a booted sim), so just use `make`.

**Signing:** `DEVELOPMENT_TEAM` is declared in `project.yml`, so regenerating is signing-safe (it does *not* wipe the team — unlike projects that set the team only in Xcode). Simulator builds/tests need no signing at all.

SPM dependencies (all declared in `project.yml`): **Adhan** (`batoulapps/adhan-swift` 1.4.0) for prayer times, **supabase-swift** (2.55.1+) for the circle, **GoogleSignIn-iOS** (9.2.0+) for one of the two sign-in providers. `Package.resolved` is refreshed by CI after a dependency change — never hand-edit it, and pull the bot commit before pushing again. `SalahBuddy.entitlements` (Sign in with Apple, `aps-environment`, and since v5 the App Group + shared keychain access group) is wired from `project.yml` and lives OUTSIDE `Sources/` so XcodeGen cannot mistake it for a resource. It is the APP's file — an extension gets its own rather than sharing this one. In `keychain-access-groups` the ORDER matters: the first entry is the process's default group, so the app-identifier group stays first (see the comments in the file).

### The backend (`backend/`)

```
backend/supabase/migrations/*.sql   # schema, RLS, column-scoped grants, triggers, RPCs — applied in order
backend/supabase/functions/         # Deno: notify (push), retention (photo sweep), sweep-orphans (auth.users shells), _shared/
backend/tests/run_sql_tests.sh      # scratch DB -> shim -> migrations -> tests/sql/*.sql -> seed twice
backend/tests/deno/                 # unit tests for the function helpers (no network, no permissions)
```

Two hard constraints for any cloud session, both real and both already worked around:

- **No Docker**, so `supabase start` is not an option, and **`*.supabase.co` is blocked by egress policy** — you cannot reach the staging project from here. SQL runs against a plain local Postgres with `backend/tests/shim/` applied (it fakes `auth.*`, the API roles, and — deliberately — Supabase's default `public` grants, so the migrations have to revoke for real). `backend/tests/run_sql_tests.sh` is the whole loop and it is FAST: run it after any migration change.
- **Deno only resolves `npm:` and `node:` specifiers** here (`jsr:`, `deno.land`, `esm.sh` are blocked). `deno check` + `deno test backend/tests/deno/` is the function suite.

Deploys are CI's job (`.github/workflows/backend.yml`, path-filtered to `backend/**`): migrations + functions go to the **staging** project on a push. There is no production project yet — see `backend/README.md`'s TODO. A second workflow, **`.github/workflows/maintenance.yml`**, is the *scheduler*: a nightly cron that POSTs `retention` and `sweep-orphans` with the service-role key (the only job in the repo that holds it).

### CI — a local pre-push hook, GitHub Actions, and Xcode Cloud

The repo is **PUBLIC** — never commit credentials, and GitHub Actions workflows must be push-triggered only (no `pull_request_target`, nothing that exposes repo secrets to fork PRs). Local CI is a **git pre-push hook** that runs `make test` on your Mac and blocks the push if tests fail. The hook is tracked at **`.githooks/pre-push`** and activated with `make hooks` (`git config core.hooksPath .githooks`) — run that once after cloning. Bypass deliberately for a doc-only/WIP push with `git push --no-verify`.

**Xcode Cloud** (see `XCODE-CLOUD.md`) additionally tests + builds every push to `staging` on Apple's free tier and uploads green builds to TestFlight internal testing — this is the path for cloud/web sessions that can't compile Swift locally. `ci_scripts/ci_post_clone.sh` regenerates the git-ignored project, stamps the CI build number, and self-heals `Package.resolved` drift. **`.github/workflows/ios.yml`** runs `make test` on GitHub's free public-repo macOS runners for fast CI feedback (no Xcode Cloud hours) and auto-commits refreshed `Package.resolved` pins after dependency changes. Manual archive/upload from Xcode still works alongside it.

## Git workflow — staging vs. production

There is **no `main`** — it was renamed to `production`. See `BRANCHING.md` for the full model. In short:

- **`staging`** is the default branch — all day-to-day work and testing happens here.
- **`production`** holds only validated work; releases are cut from it.
- Promote `staging → production` (normally a fast-forward) once a feature set is solid; never commit directly to `production`.

## Architecture

The app is a single `@main App` → `RootView` → 5-tab `TabView` (Today / Circle / Journey / Dhikr / Settings). State and rules are cleanly separated from views:

`Sources/App/` also holds **`SalahBuddyApp`/`CircleStack`** — THE launch sequence, whose order matters at every step (restore the session → bootstrap the mirror → sync profile → start `CircleSync` → refresh push, last, because it can put a permission sheet on screen) — and **`AppDelegate`**, wired with `@UIApplicationDelegateAdaptor` purely for the APNs token callbacks and foreground presentation of remote notifications.

### The clock — `AppClock` (Sources/App/AppClock.swift)
**Every time read in the app goes through `AppClock.now`, never `Date()` directly.** It applies a persisted debug offset so the in-app developer time-travel controls work everywhere. Because all logic derives from `AppClock.now` and simulated data is seeded (see BuddySimulator), time-travel is fully deterministic — jumping the clock forward/back re-derives the same world. `BuildEnv.showsDeveloperTools` gates those controls (on in DEBUG and TestFlight, off in App Store).

### State — `AppState` (Sources/App/AppState.swift)
The one `@MainActor ObservableObject` (injected as `@EnvironmentObject`). It owns `profile`, `logs`, `settings`, and the derived `todaySchedule`, persists on every mutation, and exposes everything the views render (status of each prayer, circle grids, weekly scores, challenges, recaps, places). It **delegates all scoring/rules to `GameEngine`** and holds no game math itself. Key responsibilities live here: logging prayers (`log`, `logCombined` for travel, `logQada`, `logPastMakeUp`, `undoLog`), the "can't pray" break mode, recovery (dhikr/deeds) XP, the guided tour, and `refresh()` (recomputes schedule + reconciles streaks; call on launch/foreground/day-change/settings-change).

### Rules — `GameEngine` (Sources/Core/GameEngine.swift)
**Pure, testable, no I/O, no singletons, no clock reads** — every function takes inputs explicitly. This is the single source of truth for tier math, XP, levels, perfect-day/jamaat/recovery caps, streak increment/reverse/reconcile, and weekly XP. When changing scoring, change it here and update `Tests/`.

### Persistence — `Store` (Sources/Core/Store.swift)
JSON files (`profile.json`, `logs.json`, `settings.json`) under `Store.directory`. Corrupt/missing files silently fall back to defaults. **`PrayerLog` and `UserProfile`/`AppSettings` have hand-written migration-safe decoders** — older saved data with missing fields must keep decoding, so when you add a field, give it a tolerant `decodeIfPresent` with a default.

**v5 §2: `Store.directory` is the App Group container** (`group.org.amacvoters.salahbuddymock`), not Documents — a widget is a different process and cannot read the app's Documents. Everything derives from that one property (PhotoStore, BuddyPhotoCache, the mirror, the outbox), which is why repointing it was the whole move. It **falls back to Documents** when `containerURL(…)` answers nil (test host, CI, a build whose profile lost the capability), and `SharedContainer.prepareOnLaunch()` — called from `SalahBuddyApp.init()`, before any file is read — merges Documents into the container once, idempotently, never letting an older file overwrite a newer one. Only the JSON half blocks launch; the photo directories follow on a utility queue (they are unbounded, and a blocked launch after an update is a watchdog kill).

Two consequences that bite if you forget them:

- **The migration is a COPY**, so Documents keeps a shadow of your JSON and your photos — deliberately, because the fallback build has to find something. That means **every erasure path must go through `Store.allDirectories`**, not `Store.directory`: `Store.delete`, `PhotoStore.delete`/`deleteAll`, `BuddyPhotoCache.removeEverywhere`/`sweepEverywhere`/`deleteAll` all do. A delete that visits only the live directory leaves a copy one nil `containerURL` away from being live again, which breaks SPEC-V5 §7's retention and reports invariants.
- **`circlephotos/` is the exception** — the source copy is deleted as soon as it lands. A buddy photo is somebody else's face on a 30-day clock (SPEC-V4 §4, "cheap to lose, wrong to keep"), so it gets no shadow.

The Supabase session moved with it, into the shared keychain access group (`SessionKeychain`); the old item is read once and re-stored so nobody is signed out by the update, and its removal is confirmed by a re-read behind a second marker (`legacyClearedKey`) so a failed delete cannot leave a live refresh token `signOut()` will never reach.

### The widget — `Widget/` (v5 §3, P2–P3)

A second target, `SalahBuddyWidget` (declared in `project.yml`, embedded in the app because it is listed as a target dependency), with its own bundle id (`…mock.widget`) and its own `SalahBuddyWidget.entitlements`. It ships systemSmall, systemMedium and accessoryRectangular.

**It re-derives nothing.** The app writes `widget.json` into the App Group container and the extension renders it — no `GameEngine`, no Adhan, no `BuddySimulator`, no Supabase, no `Store`, no `AppClock`. That is enforced by what the target compiles, which is only: `Widget/`, `Sources/Shared/WidgetSnapshot.swift` (the file's shape, plus the encoder/decoder pair the two processes must agree on), `Sources/Core/Models.swift` (value types, so the widget speaks the app's `Prayer`/`LogTier`) and `Sources/UI/Theme.swift` (the palette). Adding anything else to that list is the thing to argue about, not to do quietly.

- **The writer** is `AppState.publishWidgetSnapshot()`, called from `persist()`/`persistProfile()` (every local change), `applyCircleSnapshot` (every synced change), `refresh()` and `sendNudge`. It skips the disk write when the content is unchanged (`hasSameContent`).
- **The shape** is decided by `WidgetSnapshotBuilder` — PURE, in the `GameEngine` sense, and app-side only so the extension cannot call it. Its input is `AppState.gridEntries`, the same call the Today grid makes through the same `CircleDataSource` seam, which is how §9-03 ("the widget renders the demo circle too") is kept structurally rather than by remembering.
- **§7 lands at write time.** `PhotoReports`' local hide is applied as the file is written (`WidgetSnapshotBuilder.thumb`), so a reported photo's name never reaches the extension; `breakReason` has no field to travel in and `Tests/WidgetSnapshotTests.swift` asserts the file's key set to keep it that way; a person on a break appears in neither `posts` nor `waiting`.
- **`waiting[]` is the NUDGE list, not "everyone who hasn't posted"** — P4's button spends it verbatim, so it carries the Today screen's own gate (`WidgetSnapshotBuilder.nudgesAllowed`): the window must be OPEN, 30 minutes in (`nudgeGrace`, which `TodayBlocks.nudgeEligible` now reads too, so the two surfaces cannot disagree), and never the carry-over isha. Both seams answer `.waiting` for a window that has not opened yet, and `window(…)` deliberately hands back the NEXT window when nothing is open, so without the gate the tile names three people as late for a prayer two hours before it comes in. The counts (`prayedCount`/`memberCount`) are honest from the first second regardless.
- **The wiring is tested through `AppState`, not around it** (`Tests/WidgetWriterTests.swift`). The builder's own tests pass their arguments by hand, so they stay green if a production call site drops `hiddenPhotoPaths:`, `photoPaths:` or `nudgedMemberIDs:` (all defaulted) or asks `gridEntries` for the wrong `dayKey`. Those four are covered by driving a real state and reading `widget.json` back off the disk.
- **Staying current** is `WidgetSnapshot.timelineDates`/`reloadDate`: entries at the window's boundaries (free re-renders) and one `.after(…)` reload at the last of them, clamped so a time-travelled file cannot park the home screen.
- **Time in the extension** comes from the timeline entry's `date`, never a clock: the debug offset lives in the app's `UserDefaults`, which is another process's.

**P3 — photos, the setting, and the push (§5, §7, §9-02).**

- **Photos.** `PostChip` on systemMedium opens `WidgetFile.thumbnailURL(forKey:)` — the ~300px thumbnail the app cached — and falls back to the emoji when it is not there (not fetched yet, no App Group, swept at 30 days). The prefetch is `AppState.prefetchWidgetPhotos` on `applyCircleSnapshot`, i.e. when a pull lands, and it fetches exactly `WidgetSnapshotBuilder.orderedPosts`' paths: the same four posts the file names, through the same hide and the same setting, so a picture the file names and a picture the app cached cannot be different pictures. Two things it has to do because the download is ASYNC and the file's reload is not: it **reloads again when a thumbnail actually lands** (`WidgetBridge.prefetchOwesReload` — otherwise the newest face is an emoji until the window ends, since the reload was spent before the bytes arrived), and a request arriving mid-flight is **queued rather than dropped** (realtime's pull and the reconciling read moments later; the second usually carries the newer post, and on a background wake there is no "next pull" to re-ask).
- **The setting** is `AppSettings.widgetPhotoStyle` (photos / blurred / names-and-tier, default **photos** per §9-02), with a Settings row. It is applied on BOTH sides deliberately: `.namesAndTier` in the WRITER (no `thumb` is written at all, so the extension never learns the name), `.blurred` in the RENDERER (a pre-blurred file would be the widget-only photo store §7 forbids). `settings.didSet` republishes unconditionally so the change reaches the tile at once.
- **Reloads** are `WidgetBridge.reloadAllTimelines()` — the app's only `WidgetKit` import — from four callers: backgrounding, `AppDelegate.didReceiveRemoteNotification` (the §5 quiet push), `publishWidgetSnapshot` whenever a CHANGED file lands while the app is in the background, and a prefetch that put a new thumbnail on disk while backgrounded. Foreground stays rationed: §5-A's budget is ~40–70 a day and nobody is looking at a widget behind an open app.
- **The quiet push goes on EVERY post, the first one included.** `mutable-content: 1` launches the notification service extension, not the app — iOS calls `didReceiveRemoteNotification` on a suspended app only for `content-available: 1` — so an alert on its own makes the NSE reload a `widget.json` nobody was woken to rewrite. The alert stays friend-activity gated (off by default) and the reload stays ungated, which is why the two are separate fan-outs rather than one payload.
- **`NotificationService/`** is the third target, `SalahBuddyNotify` (§5-B). One file, one call: `reloadAllTimelines()` on an alert carrying `mutable-content: 1`, then `request.content` handed back untouched so the collapsed tray behaviour does not move. It compiles NOTHING else — not even `Sources/Shared` — because the app is `widget.json`'s one writer and an extension that could open the container is one somebody will be tempted to write from.

**P4 — the Live Activity, the nudge, and the Control (§6, §4, §2 tooth #3).**

- **The Live Activity is the same window, from the same file.** `PrayerWindowAttributes` (`Sources/Shared/`) is the contract; `LiveActivityPlanner` (app, PURE) turns a `WidgetSnapshot` into a plan — `.start` / `.update` / `.end` / `.restart` / `.none` — and `LiveActivityController` (app, the only ActivityKit import) performs it, called from `publishWidgetSnapshot` at the same instant the tile's file is written. Deriving the two surfaces separately is exactly how a tile saying "3 of 5" and a Dynamic Island saying 2 both end up right about their own source. `.restart` exists because attributes are an activity's IDENTITY and cannot be updated: Asr closing and Maghrib opening while nobody was looking can only be followed by retiring one and starting another. It runs **only while the window is open** — the file names the NEXT window when nothing is, and a countdown to a prayer six hours away is not a Live Activity.
- **The content state is a wire format with a Deno function on the other end** (`backend/supabase/functions/_shared/liveactivity.ts`). ActivityKit decodes a pushed state with no reply of any kind, so a mismatch is a push that does nothing, silently, forever. Three rules on both sides: no `Date`s (seconds since 1970 — two decoders we do not control would otherwise have to agree on a strategy), `tier` as a bare `String` (an unknown tier costs a colour, not the push), every field decoding with a default. 4 KB is hard and a payload one byte over is rejected whole, so the SERVER trims faces oldest-first and never the counts.
- **Push tokens live in `live_activity_tokens`, not on `devices`** — `devices.apns_token` is stable for the life of an install, ActivityKit's are ephemeral. `LiveActivityController` registers the per-activity token (with its window's `endsAt`, which is what lets the fan-out set a correct `stale-date` and retire a closed window) and the app-wide push-to-start token, both through `PushRegistrar` → `register_live_activity_token`.
- **Who STARTS one is a decision, written up in `backend/README.md` ("Who starts a Live Activity")**: the client does, because a push-to-start payload needs the window's end and the server has no prayer times — and any client that could supply one is a client already running, which would just start it locally. Push-to-start tokens are stored and deliberately never spent; the server's half is moving a running activity as the circle posts. **The same gap closes one:** `end()` is reachable only while the app is running (or from the server's `end` push, which fires when somebody else posts), ActivityKit takes no dismissal date at request time, and `staleDate` only dims — so a phone nobody touches after the window closes keeps a "window closed" card until iOS retires it. Both ends of the gap are written up in that README section.
- **`register_live_activity_token` retires a row by ACTIVITY, never by (person, window).** The tidier-looking statement silently unsubscribes the second phone on an account — both start their own activity for Asr, the second registration deletes the first's row, and phone A's Lock Screen freezes with ActivityKit reporting nothing. The schema supports ten devices per user and caps this table at 24 precisely to allow it. A restart (new `Activity.id`) is collected by the client's own delete, or by `expires_at` within twelve hours.
- **The nudge button** is `NudgeFriendIntent` on systemMedium, spending `waiting[]` verbatim (that list already carries the Today screen's gate — window open, 30 minutes in, never the carry-over isha). §4's rule is obeyed literally: the optimistic flag is written into `widget.json` inside `perform()` **before** the await, so the reload renders it. The extension reads the shared session with `Security` directly and `URLSession` — no Supabase SDK across that line — and **NEVER refreshes** (§2 tooth #3): an unusable session draws a `Link` to `salahbuddy://nudge?…` instead of a button, and the app (the one process allowed to refresh) takes it from there. `Sources/Shared/WidgetNudge.swift` holds all four pieces so the app's tests compile them.
- **`NudgeRoute` is that decision, and it is made TWICE on purpose.** A widget's render is not current — WidgetKit archives entry views when the timeline is produced, and `reloadDate` parks the next one at the window's end (up to 8h) while an access token lives about one. So the Button on screen is regularly older than the session behind it, and `perform()` re-decides **before** it writes the optimistic flag; marking first is a tile that ticks "Nudged", skips that person in `nextNudgeTarget`, and sends nothing. The route also carries §9-03: **`.demo` routes `.local`** — the file's `mode` is what says so — because `waiting[]` is populated for a simulated circle and a demo user has no account a session check could ever pass. `AppState.sendNudge` is local in demo too, so the two sides say the same thing.
- **The optimistic tick can come back out.** `NudgeRequest.landed` reads the reply (`rate_limited` = yes, exactly as `PushRegistrar.outcome` does) and `WidgetFile.retractNudge` un-ticks when it says no — but only while the file is still about the window that was nudged in, since the app republishes underneath. Without it a 401 on a rotated session leaves a chip claiming a nudge nobody received.
- **`NudgeCircleControl`** is the Control Center entry (§3's last family), and its handover is the phase's one genuinely constrained piece. Three doors are shut, in this order: `ControlWidgetTemplateBuilder` takes no branches (so no `Link` fallback), `ForegroundContinuableIntent` is unavailable in app extensions, and a computed `openAppWhenRun` is rejected by `appintentsmetadataprocessor` (it must be a compile-time literal). So the control stays headless and fails LOUDLY: `NudgeCircleIntent` throws `NudgeUnavailable.signedOut`, whose copy the system shows, and its value provider has already labelled the button "Sign in to nudge" before anybody taps it.

### The simulated circle — `BuddySimulator` (Sources/Core/BuddySimulator.swift)
There are no real friends. A fixed pool of buddies has outcomes derived as a **pure function of `(buddyName, dayKey, prayer)`** via FNV-1a seeding + `SplitMix64` (a deterministic PRNG, defined here). A buddy's post only becomes visible once `AppClock.now >= its derived loggedAt`, so the circle "fills in live" and time-travel reproduces it exactly. Buddy photos are never real images — they're seeded SwiftUI illustrations (`PostContent.illustration(seed:)`). `member(for:)` converts a buddy to a `CircleMember`.

### The real circle — `Sources/Core/Sync/` (v4)

Demo and real are mutually exclusive and chosen by **`AppSettings.circleMode`** (`CircleMode.demo` / `.real`), which **defaults to `.demo` when absent** — so every v3.9 save, and every pre-v4 test, behaves byte-for-byte as it did. `.real` is entered only by creating or joining a real circle; leaving returns to `.demo`.

Everything the Circle/Today screens need about OTHER members goes through one seam, **`CircleDataSource`**: `SimulatedCircleDataSource` (wraps `BuddySimulator`) or `RemoteCircleDataSource` (answers from the mirror). `AppState.circleSource` picks one, and `isSoloMode` is `circleSource.members.isEmpty`.

- **`CircleSnapshot`** — the offline mirror (circle, profiles, members, posts, excused days, recovery weeks, custom challenges), persisted as `circle.json` with a tolerant decoder. Every screen reads the mirror, never the wire.
- **`CircleService`** — session + circle CRUD (create/join/leave/rename, `delete_account`), and the owner of the mirror. `PhotoReports` (the §4 report action and its local hide) lives in this file too.
- **`CircleSync`** — the ONE door to the network: `postLogged`/`postRetracted`/…, a persisted FIFO **`CircleOutbox`**, a backing-off drain, a reconciling pull, and realtime as a *signal to pull sooner* (never a data path). Everything degrades to "stay offline, keep the queue".
- **`AuthService`** (Apple + Google; note the nonce rule — the provider gets `sha256Hex(rawNonce)`, Supabase gets `rawNonce`), **`PhotoSync`** + **`BuddyPhotoCache`**, **`PushRegistrar`** (APNs registration via the `register_device` RPC, and the three `notify` calls), **`Reachability`**, **`CircleError`** (the SQLSTATE → copy table).

Rules that do not bend:
- **All scoring stays in `GameEngine`.** Remote posts become `PrayerLog` values (`CircleSnapshot.prayerLogs`) and the same pure math runs on every device. There is no server-side scoring.
- **`breakReason` NEVER leaves the device.** Excused days sync as a bare flag — `CircleOp.setExcused` has no field a reason could travel in, and that is enforced by the shape of the type, not by call sites remembering.
- **Recovery XP is one opaque weekly integer** per member (SPEC-V4 §3, SCORING.md).
- **Time travel is off in a real circle**: `AppClock.offset` is pinned to 0 while `circleMode == .real`, because posting fictional timestamps to real friends breaks everything time travel exists to test. Demo keeps it.
- **DTO rule (learned twice, the hard way):** a DTO that serves BOTH the wire and the on-disk mirror must encode a column outside the INSERT grant **only** under `CodingUserInfoKey.persistingMirror` — `Store` sets that flag on its coders. A single unconditional `encode(to:)` either gets the write refused (42501) or silently drops the column on cold launch.

### Other Core pieces
- **`PrayerTimeService`** — wraps Adhan to produce a `DaySchedule` (5 `PrayerWindow`s) from coords + `CalcMethod`/`AsrMadhab`.
- **`LocationProvider`** (`.shared`) — CoreLocation wrapper; publishes `deviceCoordinate`/`placeName`; falls back to the fixed coords in `AppSettings`.
- **`NotificationManager`** (`.shared`) — schedules a rolling window of local prayer notifications (window-open + last-call) and break reminders, reading from `Store` directly (no `AppState` dependency); time-travel safe via interval triggers. `AppState` calls `.reschedule()` after relevant changes.
- **`ChallengeEngine`** — hard-coded + custom group challenges; progress computed **statelessly** from logs (yours + buddies').
- **`Badges`** — static badge conditions over the profile; `newlyEarnedIDs` awards XP exactly once.
- **`PhotoStore`** — JPEG persistence in `photos/` under `Store.directory` (downscaled, quality 0.7); logs reference bare filenames; also renders seeded demo illustrations. Buddy photos are the other store, `BuddyPhotoCache` (`circlephotos/`), and are disposable. **v5 §3 (P3): each cached buddy photo also gets a ~300px thumbnail** in `circlephotos/thumbs/`, under the SAME key, so the widget can draw a picture without a network and without decoding a 1200px original. `sweep(in:)` visits both directories — the 30-day rule is identical, the COUNT caps are separate on purpose (sharing one would halve the age at which real photos vanish from the app's own grid) — and `remove(forRemotePath:)` deletes both, so a report cannot leave the face it hid at 44pt on a home screen.

### Models — `Sources/Core/Models.swift`
Home of the shared value types: `Prayer`, `LogTier` (onTime 30 / prayed 20 / lastCall 15 / closeCall 12 / qada 5), `PrayerWindow`/`DaySchedule`, `PrayerLog`, `UserProfile`, `AppSettings`, `CircleMember`, `GridEntry`/`GridEntryState`, `PlaceTag`, `TravelPairs`, `Recharge` (tasbih/good-deeds content). Two concepts to internalize:
- **`dayKey` is `"yyyy-MM-dd"` in local time and means the SCHEDULE day a window belongs to**, not when something was logged. An Isha logged after midnight carries *yesterday's* dayKey (its window ends at today's Fajr) — this special case recurs in status, logging, streak reconcile, and undo.
- `LogTier.isInWindow` (everything but `qada`) gates photos, perfect-day, and jamaat floor.

### Design system — `Sources/UI/Theme.swift`
Soft-mint palette (bg `0xECF6EE`, white surfaces, dark-green ink `0x16382A`, **no red**), plain sans fonts (not rounded), chunky flat buttons, per-prayer and per-grid-state colors, a card-background modifier, a centered-modal component, and `Theme.spring`. Live countdowns: `RootView` publishes `AppClock.now` into the environment every second as `\.appNow` — feature views read that instead of running their own timers.

## Conventions & gotchas

- **Read time via `AppClock.now`**, never `Date()` — anything else breaks time-travel and tests.
- **Put scoring logic in `GameEngine`** (pure) and cover it in `Tests/GameEngineTests.swift` / `V2CoreTests.swift`; keep `AppState` as orchestration.
- **Adding a persisted field?** Update the model's hand-written `init(from:)` with a tolerant default so old saves still load.
- **Touching the backend?** Change the SQL under `backend/supabase/migrations/` and run `backend/tests/run_sql_tests.sh` — it is seconds, and it is the only way to find out anything here. Never edit an already-applied migration: `supabase db push` records versions and will not re-run one, so a fix goes in a NEW timestamped file.
- The spec/design history lives in `SPEC.md`, `SPEC-V2.md`, `SPEC-V3.8.md`, `SPEC-V4.md`, and `SCORING.md` — `SCORING.md` mirrors the in-app "How scoring works" and is the canonical XP reference; `SPEC-V4.md` is the contract for accounts, circles, sync, photos and push. The version markers (v3.x/v4) in code comments trace decisions back to those design sessions.
